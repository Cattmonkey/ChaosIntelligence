# 文档维护

文档与实现按同一个版本发布。`docs/` 下的 Markdown 是内容来源，运行中的 `/docs`、安装包内文档和导出的静态站都由它生成。修复内容时编辑源码文档，并在行为修改的同一变更中更新示例和验证；不要分别维护三份网页正文。

## 内容归属

| 内容 | 主维护位置 |
|---|---|
| 用户第一次成功运行 | `GETTING_STARTED.md` |
| 解压后的目录包速查与包内 README | `PROJECT_README.md`；project ZIP 根 README 从 wheel 内此页逐字复制 |
| 模型连接、路由、Settings与环境变量 | `MODEL_CONFIGURATION.md` |
| 依赖、安装、部署、数据生命周期 | `INSTALLATION.md` |
| 网页、CLI、项目与任务操作 | `USER_GUIDE.md` |
| 正式语法与语言行为 | `LANGUAGE.md`、`STDLIB.md`、`ADVANCED.md` |
| 公共集成与宿主扩展 | `DEVELOPER.md`、`SDK.md`、`HARNESS.md` |
| 版本同步、发布与更新 | `REALTIME.md`、`RELEASING.md`、`UPDATES.md` |
| 错误恢复与诊断 | `TROUBLESHOOTING.md` |
| 仓库介绍与导航入口 | 根 `README.md`、`docs/README.md` 与文档目录配置 |
| 可执行示例的期望值与输入 | `examples.json`，与对应 Markdown 示例一起修改 |

同一事实只在一个参考页完整定义，其他页面链接到它。避免在标题或多处说明中复制容易过时的版本号、模型目录和安装路径。模型名称和服务地址应明确为占位符或用户配置，不记录维护者本机账号信息。

`PROJECT_README.md` 是文档目录中登记的短页，也是 project ZIP 根 README 的唯一正文来源。此页保持无相对链接，以命令和 IDE 的 `/docs` 入口引导用户；构建器从 wheel 逐字复制，不做链接替换或另存一份长文本。不要在 `chaos/portable.py`、打包脚本或生成目录内手工维护同一使用说明。

## 教程与参考怎样组织

导航按学习任务组织，不逐版本追加功能摘要。实现历史归入 LANGUAGE_ROADMAP；SDK、IDE等参考页保留稳定标题与深链。新行为优先整合对应章节，必要时提供“前置条件 → 输入或命令 → 可核对结果 → 失败与恢复 → 下一步”的小例子，不为每次发布另建总结页。

目录项目、portable SDK 包、wheel 和托管服务应分别说明依赖与状态：project ZIP 不包含 Python 和所有第三方依赖，setup 显式准备活动环境的依赖；静态文档只负责阅读。目录 init 只创建模板，install 才从完整包部署运行环境。`.chaos/runtime` 和 `.chaos/deps` 是初始布局，替换后以 status 返回的活动路径为准；用户配置和数据库仍在项目 `.chaos` 根下。不能用“覆盖新包”“重新安装”概括所有更新方式，应链接到具体 replace／旧项目迁移／托管更新流程。

模型教程使用环境变量名和占位符，不写真实 key、私人地址或未授权账号。模型连通、推理质量与纯文档示例是不同验收。

## 修改流程

1. 先对照实际实现、CLI `--help`、公共 API 和测试确认行为，区分已实现功能、可选依赖与未来范围。
2. 修改对应 Markdown，同时更新导航入口与必要交叉链接。使用相对 `.md` 链接，确保源码、安装包和静态站都能解析。
3. 对可独立运行的 Chaos 示例登记稳定 ID、输入、模块文件及预期 JSON 结果；错误演示、片段或需凭据的网络示例应明确说明前置条件。
4. 运行文档检查，再执行与行为相关的回归及完整发布基线；未登记的 shell／Python 教程命令须另在临时工程中实际验收。
5. 构建静态站，检查目录、搜索、代码块、表格、跨页链接和窄屏排版；wheel 安装后再从 checkout 外验证文档入口。

代码围栏应明确标注语言：Chaos 用 `chaos`，Python 用 `python` 或 `py`，命令行用 `sh`／`shell`，数据用 `json`，文法或纯文本用 `text`。语言标签决定显示方式，不从内容猜测；Chaos 高亮和提示来自实际分析器，Python 使用标准库词法器，其他标签保留原文。代码块可使用 `chaos example=示例ID` 标记登记示例；ID 应与 `docs/examples.json` 条目一致。未标记的代码块只作为展示，不会自动运行。登记示例应确定、无密钥、无网络及无外部副作用，期望结果必须经过解释器验证。不要让文档检查执行任意 shell、Python 或模型调用。

### 有宿主和实时交互的示例

`progress_emit`／`guidance_receive` 依赖真实 Run；不能把带等待或外部效果的程序直接登记为纯 `Framework.evaluate` 示例。保持 `docs check` 的确定性边界，另用临时 Framework／HTTP 服务验收示例文件。`examples/live-progress.chaos` 验证逐步进度，`examples/interactive-progress.chaos` 验证指导原样投递及未收到指导的分支；对应测试为 `tests.test_realtime_transport` 与 `tests.test_interactive_progress_example`。

用户教程里的目录命令还需从干净 project 包运行，确认 `--stream` 的事件和 `run.result` 包装、JSON 输入及退出码；网页指导与终端指导需要各自交互验收，不能用最终值测试代替。对话/源码在当前页面断线时保留，与刷新关闭后的恢复范围要分别描述。同步核对 README、随包速查、入门路径、使用指南和 API 参考的入口，完整协议只在对应参考页定义。

## 自动校验与本地预览

```sh
python -m chaos docs check
python -m unittest discover -s tests -v
python -m chaos docs build --output ./docs-site
python -m http.server 8000 --directory ./docs-site --bind 127.0.0.1
```

打开 `http://127.0.0.1:8000` 检查导出效果。`docs check` 校验本地文档链接及登记的可执行 Chaos 示例；网络服务和真实模型可用性不由这个检查证明。HTTP API 页面同时提供机器可读 `/api/v1/openapi.json` 契约入口，端点参考表随实现生成，减少手工抄写漂移。

静态导出包含所需 HTML、CSS、JavaScript、原文与示例，不需要 CDN。有效的 Chaos 片段若格式化后有变化，会同时包含预计算的阅读副本；高亮、类型／签名提示与排版切换可离线使用，复制保留原文。预览时同时检查原始及格式化视图、键盘与触屏提示，并确认无效片段仍完整可读。构建器只允许更新由其标记的生成目录，拒绝任意已有内容或符号链接；使用专门的输出目录，不存放用户数据。静态站用于阅读，不提供项目运行、配置或后台任务 API。

## 发布门槛

发布前确认新行为有相应文档与可复现示例，文档检查和完整测试通过。发布构建默认运行测试，并验证 wheel 包含源码、网页、文档及示例；不应为绕过失败而使用 `--skip-tests`。

版本更新来源是 `chaos/version.py`。已交付版本不可原地改写内容；文档或示例修订也发布新的补丁版本，保留原版制品用于真实迁移验收。分别核对新 wheel、project ZIP、portable ZIP 和静态站里的文档来自同一版本，不只替换一个可变下载文件。签名发布按 [发布流程](RELEASING.md) 执行；静态文档上传到维护者实际控制的托管地址。先完成本地构建与检查，再发布生成目录。没有配置真实托管时，只能称为本地或随服务在线文档，不能声称公网已经发布。

使用新包重启服务后，应用 `/docs` 与选中的运行版本一致；仅修改磁盘源码或生成 ZIP 不代表已经运行的服务升级。单独静态站需要随同版本重新构建和部署。维护旧版本文档时使用对应源码版本构建到不同目录，避免给旧用户展示新版本才能支持的命令。目录环境变更还须完成真实上一版的“迁移 → 运行 → 替换／回退 → 再升级”验收，保存制品哈希与用户数据保持证据，不能只运行版本夹具测试。

## 持续维护策略

维护动作属于代码审查、测试和发布流程：每次改变 CLI、语法、公共 API、配置、默认值、部署路径或更新行为，都检查本页的内容归属并同步修改。新增页面必须加入导航和检查范围；删除或更名页面必须修复链接。

这里没有自动在远程改文档的守护程序，也没有预先启用定时发布任务。自动校验保证登记契约不悄悄失效，人工评审负责教程完整性、解释准确性和示例适用性。若团队另有 CI，应把 `python -m chaos docs check` 和完整测试作为合并或发布门槛；定时巡检或远程发布需由维护者在实际环境另行配置。
