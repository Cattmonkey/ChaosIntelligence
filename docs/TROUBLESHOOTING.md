# 故障排查

先区分错误发生在哪一层：Python 安装、语言检查、项目运行、HTTP 服务、模型请求或外部工具。保留失败命令、版本和最小输入，通常比反复重启更容易定位。

## 目录项目先查这里

在发生问题的工程目录先执行以下命令；记录输出中的版本与路径，不要仅凭解压包的文件名判断当前版本：

```sh
python3 --version
./chaos --version
./chaos status
./chaos check
```

Windows 将 `python3` 换为 `py -3`。`status` 显示活动运行时、上一环境和配套依赖是否匹配，它不是模型或硬件的健康检查；旧项目可能尚无此命令。运行时已经缺失或损坏时，版本和状态命令本身也可能失败，保留原错误继续定位。

| 现象 | 检查与恢复 |
| --- | --- |
| 没有全局 `chaos` 命令 | 在完整项目目录使用 `./chaos`；目录入口不要求全局安装另一份 Chaos |
| 提示缺依赖，或 `dependenciesReady` 为 false | 停止本项目 IDE／程序，再执行 `./chaos setup`。依赖位于活动 `runtime` 同级的 `deps`；只有初始环境使用 `.chaos/deps`。正常 run／IDE 不会自动联网补装 |
| `Project environment is in use`／`Another project IDE is already active` | 正常退出本项目正在运行的 IDE、CLI 或环境维护进程后重试；不要删除锁文件强行并发替换 |
| 旧项目不认识 `replace`／`status` | 在解压后的新版 project 包目录执行 `./chaos install /absolute/path/old-project`。迁移官方旧启动器，保留目标工程源码、设置和数据；自定义旧启动器需显式迁移 |
| `Project chaos.py was customized` | 保留自己的启动器和项目备份，按[更新说明](UPDATES.md)处理迁移条件，不直接覆盖定制入口 |
| `No previous environment is available` | 当前没有可回退目标；停止重试 rollback，使用已验证的工程备份或按完整安装流程处理 |
| 新包完整性、Python／环境协议校验或候选自检失败 | 活动环境不会因此切换。核对可信包是否完整、Python 是否满足该包要求；不要编辑清单、版本或环境指针跳过校验 |
| 内置运行时缺失、损坏或被另一份包遮蔽 | 先备份整个工程并保留报错；定位活动环境，不只查看初始 `.chaos/runtime`。不要依靠全局包掩盖缺文件，也不要覆盖解压新包到旧工程；恢复边界见下文 |
| `Unknown configuration field`／配置结构错误 | `settings.json` 必须符合 Settings 的完整结构，不能把 `{}` 或 `chaos.project.json` 内容作为替代。保留错误文件，从有效备份恢复，或另存该文件后通过[配置页面／脚本](MODEL_CONFIGURATION.md)重新建立设置 |
| IDE 地址不是 8765 | 目录 IDE 默认选择空闲端口，以 `project.ready` 输出的 URL 为准 |
| CLI 结果不在 IDE 历史里 | 默认 CLI run 用内存；`--persistent` 用 `.chaos/cli.sqlite3`，IDE 用 `.chaos/project.sqlite3`，这不是数据丢失 |
| `fmt` 后文件没有变化 | `fmt` 只把格式化文本输出到终端。可使用 IDE 的格式化并保存；命令行要先输出到不同文件检查，不能重定向覆盖正被读取的源文件 |
| 搬移后第三方扩展不能导入 | 核对 Python／系统／架构兼容性，在目标环境显式 setup；不要将旧 venv 当作可搬移运行包 |
| 同步等待或停止 | 暂时语法错误会等待修正；冲突或入口改变会停止并保留恢复记录。先保存双方并合并，不删除记录强制覆盖 |
| setup 提示 `deps.previous` 需处理 | 它位于当前环境，未必是初始 `.chaos/` 下。保留旧目录并检查上次安装输出，按提示恢复或整理后再试，不盲目删除已有依赖或用户数据 |

setup 先安装到临时目录；依赖安装失败时保留原依赖。replace 在校验与自检成功前保留原环境；失败的候选不用于下一次启动。成功替换后如缺少配套依赖，需要显式 setup；这与包替换失败是不同状态。

rollback 需要启动器能够加载管理命令，而且上一环境仍存在、完整、兼容当前 Python。若当前运行时已经无法导入或环境元数据损坏，不能保证从该目录执行 rollback。先保留源码、设置、数据库和完整环境副本，再结合具体错误恢复可信的完整备份；不要直接手改 `.chaos/environment.json` 或删掉版本目录尝试修复。安装、替换与旧版本迁移的完整流程见[更新说明](UPDATES.md)。

下面的全局 `chaos`／venv 诊断适用于源码、wheel 或独立服务安装。模型请求失败另外按[模型配置](MODEL_CONFIGURATION.md)检查配置来源、路由与账号权限；不要把 Key 贴入诊断输出。

## 安装与启动

| 现象 | 检查与处理 |
|---|---|
| `chaos: command not found` | 激活安装包的 venv，或使用该环境的 `python -m chaos`；确认 `python -m pip show chaos-intelligence` 指向预期环境 |
| `No module named chaos` | 在正确 venv 安装源码或 wheel；不要依赖从其他目录偶然导入 checkout |
| 缺少 `openai`、`cryptography` 等依赖 | 用同一个 Python 运行 `python -m pip install .` 或安装可信 wheel；检查 `python -m pip check` |
| Python 版本不兼容 | 使用 Python 3.9+ 并重新创建 venv，不要直接搬动已有环境 |
| 端口占用 | 保留原服务并改用 `chaos serve --port 8877`，或者正常关闭已确认的旧实例 |
| 页面为空或缺资源 | 核对版本与 wheel 是否完整；源码方式确认 `web/` 存在，安装方式重新安装完整发行包 |
| 数据重启后看似丢失 | 检查工作目录及 `--db`、`--config`、`--state-dir` 是否与原启动一致；相对路径可能指向另一目录 |
| 数据库已有活动引擎 | 一个数据库只能由一个 Framework/服务持有；其他进程改用 HTTP Client，不要删除锁文件强行双开 |

原独立服务的基本诊断（目录IDE需把下例8765换成终端实际端口）：

```sh
python --version
python -m chaos --version
python -m pip check
python -m chaos docs check
curl --fail http://127.0.0.1:8765/api/v1/health
```

`docs check` 检查文档内部链接与登记的确定性 Chaos 示例；它不是模型、浏览器或远程更新服务的连通性测试。

## 语言与程序运行

| 现象 | 含义与处理 |
|---|---|
| `syntax_error` 或带文件/行列的解析错误 | 运行 `chaos check file.chaos`，检查引号、分号、块、导入路径和入口文件 |
| `check` 成功但 `run` 失败 | 检查只覆盖结构；运行时仍会验证输入类型、工具权限、数据与预算 |
| JSON 输入解析错误 | `--input-json` 必须是 JSON；字符串写为 `'"hello"'`，布尔用 `true`/`false`，空值用 `null` |
| 类型契约失败 | `Int`、`String`、`Bool` 等不能靠隐式转换代替；特别是布尔不是数字，条件必须为 Bool |
| 未定义名称或模块成员 | 核对词法作用域、显式 `export` 和相对导入；模块不读取任意服务器文件 |
| 工具未授权 | 同时检查项目 `capabilities`、主体 `tools` 和工具注册名称；`graph.patch` 只走平台事务 |
| `resource_limit`、超时或递归深度错误 | 缩小输入、拆分工作，采用迭代/尾递归/fold；预算和取消不能靠语言 try/catch 消除 |
| 输出函数描述符 | 函数等运行时值不能作为原生 JSON 跨边界传播；返回可序列化数据，或在同一执行内调用函数 |

使用源码追踪定位有界执行步骤：

```sh
chaos run file.chaos --input-json null --trace > result.json 2> trace.jsonl
```

追踪有条数限制，截断不代表程序停止。正常 CLI 错误也写 stderr，失败时检查退出码和错误对象。SDK 中 `RunFailed.run` 保存终态运行记录；`wait()` 返回终态，而 `result()` 只接受 `completed`。等待超时不会自动取消运行，需要显式 `cancel()`。

解释器限制源程序大小、集合长度、展开深度、整数位数、计算步数及非尾递归深度。共享运行预算还覆盖工具和智能体调度。不要通过无限提高限制来处理逻辑死循环；具体语义见 [语言参考](LANGUAGE.md) 和 [形式语义](SEMANTICS.md)。

## 网页、API 与同步

先核对浏览器当前地址、终端显示的服务地址及 `/api/v1/health` 中的版本。不同项目目录可能使用不同端口；更新磁盘上的包不会替换已经运行的旧服务。正常停止旧服务后再从选定环境启动，保留当前未保存内容。

| 现象 | 检查与恢复 |
| --- | --- |
| 连接显示恢复中，事件暂时不增加 | 先确认服务仍在运行、网络和代理允许 SSE；同一页面会从已处理游标补读。不要把一次断线当作任务失败，也不要反复提交任务 |
| SSE 大约每25秒重新连接 | 服务会轮换连接。短暂重连属于正常行为；持续无进度时检查真实任务状态、最后事件和程序是否等待输入 |
| 有运行中“结果”但任务仍未结束 | `progress_emit("result", ...)` 仍是公开进度；只有运行终态与最终 output 表示程序结束。程序可能还要等待指导、工具或其他 Task |
| 看不到新事件，底部有“跟随最新” | 当前正在阅读历史，点击该按钮回到底部。界面只显示有界窗口；完整记录使用事件接口分页读取 |
| 指导一直显示“已入队” | 程序尚未执行接收点，或指导目标不是预期 Bot／角色。先用[交互教程](REALTIME.md#从运行到追加指导)验证；普通计算不会自动消费自然语言 |
| 指导显示“运行已接收”，结果仍不符合要求 | 接收仅证明消息交给了程序。检查源码如何使用 `message.input`、Bot 的采用状态及后续动作；不能把接收回执当作效果完成 |
| 助手已显示回答，但还在“同步最后的执行事件” | 最终快照先于流的尾部到达。保留当前页面并等待事件同步；持续停留时检查连接及服务，先保留未发送文字，不要重复提交同一需求 |
| 助手断网后“发送”仍不可用 | 已有任务仍被跟踪，防止重复启动。恢复后会同步结果；需要停止时使用该助手的“停止”，并确认停止请求已送达 |
| 首次发送后报网络错误，页面还没有任务 ID | 提交是否被服务接受可能未知。先检查该项目的助手历史／后台任务列表，再决定是否重试；不要自动重发会产生副作用的 POST |
| 旧提案不能应用 | 应用基准的草稿、入口或项目版本已改变。保留当前代码，按新草稿重新请求；不要覆盖新编辑来强行套用旧提案 |
| 页面刷新后未发送文字或草稿不在了 | 断线保护针对保留着的页面内存，不是全部输入的自动持久化。查已保存项目、明确导出的备份和编辑器本身的恢复记录；刷新前先保存／导出源码、保留未发送文字 |
| 409／项目版本冲突 | 读取最新版本，导出自己的草稿后比较合并，再用新版本提交；重试旧版本不等于合并 |
| 工作区 watch 停止 | 检查 `.chaos-conflict.json`，保留 `.chaos-before-pull.json` 和 `.chaos-replaced-*` 中的恢复文件；按[实时同步](REALTIME.md)处理 |
| `Untrusted Host or Origin` | 使用实际监听的受信地址，检查代理是否改写 Host／Origin；来源校验不是多人认证系统 |
| 503 `updating` 或更新时暂时断开 | 更新正在等待任务或重启。恢复后读取状态，避免自动重发可能重复产生副作用的操作 |

**停止观察和取消工作不同。** 关闭网页、收起助手或断开 SSE 不会替你取消服务中的任务；服务需要继续运行。本地 `run --interactive` 则拥有执行生命周期，`/cancel`、Ctrl-C 或 Ctrl-D 会请求取消并等待清理。取消不会撤销已经发生的文件写入、记忆和外部动作；判断停止是否完成，应读取实际终态，而不是只看按钮已经点击。

在 POSIX 终端使用 `--interactive` 时，stdin 和 stdout 都必须是 TTY；不能和 `run -` 同用。Windows、管道和输出重定向使用 `--stream`，需要引导时用网页或 SDK／HTTP。`--stream` 的逐行事件与普通 run 的单个最终 JSON不同，成功流以 `run.result` 结尾，失败通过退出码和错误状态区分。操作示例见[用户指南](USER_GUIDE.md#使用命令行)，事件接口见[实时交互](REALTIME.md)。

## 模型和工具

| 现象 | 处理 |
|---|---|
| `Provider key is not configured` | 在 `/control` 为实际路由保存密钥；嵌入 Framework 如需磁盘配置，显式传 `Settings()` |
| 401 / 403 | 核对账号、密钥和服务权限；运行时不会用自动切换掩盖凭据问题 |
| 模型不存在或无权限 | 核对提供方地址、完整模型 ID、角色及 agent 覆盖；`/models` 列表不保证推理权限 |
| 配置已保存但本次仍用旧模型 | 新配置在下次请求/迭代生效；观察路由事件及配置版本 |
| 自动路由选择了不同模型 | 检查角色的 `families`、发现目录及 `autoUpgrade`；需要固定模型时关闭自动升级 |
| 浏览器可选依赖或 Chromium 缺失 | 在服务所用 Python 环境安装 browser extra，并以服务账号完成 `python -m playwright install chromium` |
| Codex 可执行文件找不到 | 核对独立 CLI 安装和 `codexPath` 绝对路径；它不借用 Codex App 登录或运行时 |
| 语言/图智能体拒绝 codex | 将其路由为 native；独立 Codex 后端用于后台任务，当前没有语言工具回调桥 |
| 插件服务不可用 | 检查 `/control` 插件启用状态、依赖和失败状态；不要从网页填入任意 Python 导入路径 |
| 重启后任务 interrupted | 先检查已完成产物与外部效果，再显式恢复，避免重复副作用 |

不要把真实密钥贴入问题报告。服务配置的公开视图会隐藏密钥，但仍可能含内部地址、模型名称和工作目录；发送前再次审阅。代码输出、源程序和任务内容也可能包含私有数据。

## 更新与文档问题

目录项目的 `replace` 使用本地完整包，不要求在线 feed。独立服务的更新页面显示“未配置”表示尚无可信 feed 和公钥，不是自动发布失败。签名、下载、版本兼容或候选自检失败时保留当前版本，并按 [更新安装](UPDATES.md) 读取错误状态。不要替换成未知公钥或手工修改版本指针规避验证。

目录项目先用 `./chaos status` 确认活动 `runtime`，并打开本项目当前 IDE 地址下的 `/docs`；初始 `.chaos/runtime` 在替换后可能已是旧版。已安装 CLI 的 `chaos docs path` 显示该 CLI 使用的文档目录。源码改了而网页文档没变时，检查正在运行的服务是否来自另一个 venv 或旧 wheel；普通 wheel 安装需重新构建/安装并重启。静态文档需重新 `chaos docs build` 并发布生成目录。文档构建目录属于生成物，不要在其中保存用户数据。

## 提交可复现问题

准备以下最小证据：Chaos 与 Python 版本、操作系统、安装方式、失败命令、最小 `.chaos` 文件、脱敏输入、退出状态，以及必要的事件 ID/版本/错误码。删除密钥、私有路径、订单或用户数据，避免上传整个配置目录、数据库、环境变量列表或完整任务产物。对真实服务专属问题，注明是否能用本地纯计算程序复现。
